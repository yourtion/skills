# 运行器有效性与测试隔离

## 验证实际执行，而不只验证兼容范围

先查当前 Stryker core、runner、Node 和测试运行器的官方兼容说明，再用项目真实配置验证。
peer dependencies 满足、配置能加载、dry run 通过，都不能证明测试名称过滤与变异执行正常。
多 project、跨包别名、框架插件和不同 Vitest 主版本需要特别核对；不要把某次接入选用的版本组合永久写成通用要求。

选择有真实测试覆盖、包含业务判断的小文件，使用独立的临时 incrementalFile 执行入口要求的三轮验证：

- 首轮和 `--force` 轮实际生成并执行变异；具有明确影响的错误应被现有测试检出，例如登录条件从 `&&` 变成 `||`。
- 检查关联测试名称、报告中的 `coveredBy`、静态标记及 runner 提供的 `testsCompleted` 等证据。
  首轮或强制轮中，已有覆盖或属于静态变异的 `Survived` 却执行零测试，应排查测试过滤、project 选择和加载错误，不能直接接受为可信存活结果。
- `NoCoverage` 可以合法地没有关联测试；增量复用也不能仅凭本次执行数判断。区分没有覆盖、已复用结果和应执行却未执行。
- 第二轮确认复用数量，强制轮确认不复用；不要让旧基线掩盖升级后的运行器问题。

发现兼容问题时，优先选择经真实验证的受支持版本。用户允许升级 Node 或测试运行器时，
同时调整 engines、锁文件、类型依赖、CI 和容器构建，保留普通测试与编译检查。

## 测试加载失败不能被误报为存活

测试运行器可能在文件或 suite 层面报告错误，尚未产生任何失败的单条测试。
排查这类结果时同时检查文件级错误、进程输出和实际测试执行数，不能只统计 failed test cases。

- 未激活变异的原始测试加载失败，应中止本次变异运行。
- 变异导致无法加载测试时，按当前 runner 协议保留运行时错误原因，例如 `RuntimeError`；不能误记为 `Survived`，也不能记为 `Killed` 来提高得分。
- Vitest 等运行器可能返回序列化对象而非原生 `Error`。格式化错误时应保留 message/stack 或可读对象信息，避免错误处理再次崩溃。

若已复现上游缺陷且需要补丁，把补丁与精确依赖版本、包管理器配置和锁文件提交到目标仓库，
不能只修改 `node_modules`。仅为已确认的问题补充有意义的真实运行器回归：正常失败、文件级加载失败、
原始测试失败，以及相应的序列化错误等场景。升级依赖时重新验证，移除不再需要的补丁。

带补丁的干净安装必须在 CI 和使用相同锁文件的容器安装阶段生效；构建上下文需包含补丁文件。
运行器或补丁变化应使兼容性键失效，已有不可信结果须强制重建后再发布共享基线。

## 先解决隔离问题，再扩大并行度

变异会反复导入和执行源码，原先未暴露的副作用可能持续累积：

- CLI 入口的导入不应意外启动服务；区分可导入模块和真正的启动入口。
- 用 `mkdtemp` 为测试或 worker 创建独立目录，避免固定临时文件名。清理测试自己创建的资源，不导入另一个测试服务器来做清理。
- 在 teardown 中关闭服务、连接、订阅和定时器；测试时钟相关逻辑时控制必要的时钟，并在用例结束后恢复。
- 固定端口的 E2E 应与并行变异隔离，保留在原有 CI 中；确需参与变异时先解决端口分配与生命周期问题。

这些问题通过资源隔离解决，不能仅靠放大超时、删除业务断言或把所有测试串行化来掩盖。

## Monorepo 构建与测试选择

跨包导入依赖 `dist` 或生成产物时，先执行项目已有的必要构建；变异仍指向业务源码。
在干净安装环境确认构建、类型检查和普通测试，并检查 CI/容器是否具备相同输入。
报告、临时沙箱和本地生成目录应按项目约定忽略，避免进入后续沙箱或容器构建上下文。

默认保留模板的 `vitest.related: false`。若实测耗时需要启用 related，先比较原有套件与关联选择下的
覆盖集合（含静态变异与跨包导入），再运行代表性的静态、非静态和已知可检出变异验证结果。
覆盖集合相同本身不能证明断言等价；无法确认时保留完整测试选择，不只根据测试数量减少就宣布优化有效。

## 根据报告改进测试

复用真实业务模块：路由测试应挂载生产路由并模拟外部依赖，schema 测试应导入共享 schema，
避免自建假路由或复制一份生产规则。重复的路由存在性检查可以合并，业务行为、输入校验、
返回值、错误状态和副作用需要实际断言。

边界用例要真正触发约束。例如 LRU 测试需使用足够小的容量并验证被淘汰的键，
时钟和并发边界需在旧实现上复现失败、修复后通过。仅增加测试数量或检查对象存在无法证明质量提高。
逐项审查存活变异；等价变异与日志等低价值差异需说明判断，优先修复业务缺口。
